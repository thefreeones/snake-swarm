## 一、设计哲学

### 1.1 核心信念

"不追求零错误，追求错误能被快速识别并低成本修正。"

这意味着：
- 系统不假设任何单一组件完美——包括裁决层自身
- 每个组件预设"自己可能犯错"，相邻组件放置检测手段
- 用流程的严谨性对冲认知的局限性
- 错误发生时，系统必须能识别、定位、修复、学习——形成闭环

### 1.2 四条设计原则

| 原则 | 含义 | 实验来源 |
|------|------|---------|
| 异构优于同质 | 不同模型有不同认知盲区。异构组合将互补性转化为系统能力 | P0：Claude单法官38% vs 三法官100% |
| 证据优于结论 | 插件不给出判断，只输出标准化证据。法官基于证据裁决 | P0：S2案例插件展示数值反例后法官翻转 |
| 信息隔离打破认知盲区 | 修复失败时由异构模型在不看原代码的情况下重写 | P7：黑箱重写将防御层从1层增至4层 |
| 确定性优先于概率性 | 规则引擎能做的事不消耗LLM | P4：确定性审计节省12,905 tokens |

### 1.3 实验修正的设计直觉

v0.3原设计中的若干假设被实验修正：

| 原假设 | 实验发现 | 修正 |
|--------|---------|------|
| 蛇尾纯记录是最优的 | deviation_log（含自述）比纯记录多捕获143%偏离 | 蛇尾增加7字段结构化自述，含[我无法确认]强制字段 |
| 法官自然能交叉验证 | 法官读devlog后反而更不警觉（log催眠效应） | 强制反轻信4步指令，响应率0/4→4/4 |
| 多法官必然优于单法官 | 同模型双法官的一致性可能是训练偏差的复现 | 至少1个异构模型；1:2分层处理（异构孤判100%深挖，同模型孤判5%抽样） |
| 修复只需在原代码上调整 | 修复蛇与原蛇身的同源性导致共享盲区 | A+B四阶闭环：修复失败→黑箱重写（信息隔离） |

## 二、两种运行模式

蛇群当前支持两种模式，已通过实验验证：

### 模式A：缺陷检测与修复（Bug Fix）

```
给定代码 → 蛇头分析 → 蛇身修复 → 三法官审查 → 审计验证 → 交付patch
```

**已验证能力：**
- 缺陷检出：17个构造用例 100%（P0-P3）
- 缺陷修复（直线式函数）：python-slugify 5/5，与维护者方案100%一致（P8）
- 缺陷修复（框架约定）：validators 2/4，暴露@validator装饰器盲区（P14）
- 成本：8,400→~5,000 tokens/bug（-40%）（P9-P13）

### 模式B：项目构建（Project Build）

```
给定需求 → 蛇头拆解（模块+契约） → 蛇池并发实现 → 集成 → 法官审查 → 交付项目
```

**已验证能力：**
- CRUD工具：matchlog CLI — 4模块，3智能体并发，首次集成即通过（v0.5）
- 数据管道：Student Score Analyzer — 4模块，含字段级数据契约验证（v0.6-B）
- 已验证的依赖拓扑：线性（matchlog）和管道式（score analyzer）

**两种模式共享的核心机制：**
- 蛇头分层分析（L1/L2→轻量DeepSeek，L3+→Claude）
- 三法官异构裁决（DS-t0.3 + DS-t0.7 + Gemini-t0.3）
- 批量法官审查（N个模块/修复打包一次调用）
- 确定性审计（L1/L2零token规则引擎）
- 蛇改进回路（成功经验→模式提取→注入未来任务）

## 三、五层协同架构

```
┌────────────────────────────────────────────────────┐
│                    学习层                            │
│      模式提取 → 注入snake head → 成本次线性下降      │
│      已验证: 5bug→3模式, 密度0.6/bug (P9)          │
├────────────────────────────────────────────────────┤
│                    审计层                            │
│      L1规则(零token) → L2回归 → L3语义(按需)        │
│      8种AST危险模式, 90%场景零token (P4,P8)        │
├──────────────────────┬─────────────────────────────┤
│      裁决层           │          修复层              │
│  三法官异构投票        │   A: 异构诊断→按指令修改     │
│  反轻信4步指令         │   B: 黑箱重写(信息隔离)      │
│  1:2分层处理           │   降级触发: 确定性规则       │
│  批量审查(-69%t)       │   已验证: P4,P7,P8,P14      │
├──────────────────────┴─────────────────────────────┤
│                    执行层                            │
│  蛇头(分层) → 蛇身(执行) → 蛇尾(自述)               │
│  推理增强插件(证据提供, 不做判断)                    │
│  已支持两种模式: Bug Fix / Project Build            │
└────────────────────────────────────────────────────┘
```

### 3.1 执行层

| 组件 | 技术 | 已验证 |
|------|------|--------|
| 蛇头(重) | Claude Sonnet 5，完整prompt | P0-P3,python-slugify |
| 蛇头(轻) | DeepSeek V4 Pro，精简prompt | P11:-63% token，根因一致率100% |
| 蛇身 | DeepSeek V4 Pro(t=0.3)，两份日志 | P2:devlog+143%A组偏离 |
| 蛇尾(自述) | 7字段结构化自述+[我无法确认]强制字段 | P2:修正蛇尾纯记录假设 |
| 蛇尾输出分类: | **事实字段**(系统自动填充: diff行数/测试通过数/文件变更列表) **推断字段**(模型生成, 必须标注证据来源) **不确定字段**([我无法确认]强制列出) | 自述不作为法官通过依据, 仅作为审查线索 |
| 推理增强插件 | 规则引擎，仅提供证据 | P0:S2插件翻转DeepSeek漏判 |

**蛇尾自述校验规则（v0.7新增）：** 若蛇尾声称"已验证"但系统无对应测试或运行记录 → 自动标记高风险。蛇尾自述中每个推断字段必须引用至少1个evidence_id或系统事实。

**Evidence Pack 标准化（v0.7新增）：** 所有插件输出统一的证据包格式，法官裁决必须引用evidence_id：

```json
{
  "evidence_id": "ev_001",
  "task_id": "task_123",
  "source": "static_analyzer | test_runner | dependency_graph | runtime_trace",
  "type": "error | warning | metric | diff | log | contract",
  "severity": "info | low | medium | high | critical",
  "file": "src/validators/url.py",
  "line_range": [45, 52],
  "content": "观测到的具体内容",
  "structured_data": {},
  "confidence": 0.95,
  "limitations": ["仅检查了同步路径"]
}
```

**插件约束：** 插件不能输出"我认为应该通过""该修复正确"等判断性结论。插件只能输出：观察到什么、证据是什么、不确定项是什么。没有证据支撑的裁决结论必须降低置信度。

### 3.2 裁决层

**v0.7 法官角色化设计。** 三法官不再仅依赖模型异构（同模型不同温度可能共享训练偏差），而是角色化——每个法官有独立视角和证据输入。角色超越具体模型，模型可替换而系统结构不变。

#### 角色化法官配置

| 法官 | 角色 | 关注点 | 证据输入 | 默认模型 |
|------|------|--------|---------|---------|
| 法官A | **语义正确性** | 业务逻辑、函数语义、边界条件、意图一致性 | diff + 原始需求/issue + 代码上下文 | DeepSeek V4 Pro(t=0.3) |
| 法官B | **测试证据** | 测试覆盖变更、是否可复现、是否回归、测试质量 | diff + 测试结果 + 覆盖率报告 | DeepSeek V4 Pro(t=0.7) |
| 法官C | **架构/契约** | 接口契约、模块边界、依赖关系、框架约定、API兼容性 | diff + 类型签名 + 依赖图 + 框架约定规则 | Gemini 3.6 Flash(t=0.3) |
| 仲裁 | — | 冲突场景下的终裁（非第四个普通法官） | 三法官输出 + 全部证据包 | Claude Sonnet 5 |

**角色异构四维度：**

| 异构维度 | 法官A | 法官B | 法官C |
|---------|--------|--------|--------|
| 模型供应商 | DeepSeek | DeepSeek | Google |
| 模型家族 | V4 Pro | V4 Pro | Gemini Flash |
| 推理策略 | 语义理解型 | 证据验证型 | 规则/契约型 |
| 证据视角 | 代码diff视角 | 测试视角 | 架构/契约视角 |

至少满足其中两项异构即构成有效角色分化。

#### 法官独立性约束

| 规则 | 说明 |
|------|------|
| 先独立后汇总 | 法官不能看到其他法官的初始结论 |
| 先输出证据再给判断 | 每法官输出证据链→判断→置信度 |
| 禁止复制结论 | 禁止直接复制其他法官结论 |
| 多数派必须独立证据 | 对多数派结论必须给出独立证据链 |
| 少数派不得丢弃 | 所有少数派意见进入deviation_log |

#### 标准化裁决输出

每个法官输出结构化JSON：

```json
{
  "judge_role": "semantic | test_evidence | contract",
  "verdict": "pass | fail | uncertain",
  "confidence": 0.85,
  "severity": "P0 | P1 | P2 | P3",
  "evidence_refs": ["ev_001", "ev_002"],
  "reasoning": "判定理由",
  "counterevidence": "对立面证据",
  "uncertainty": ["无法确认项1", "无法确认项2"]
}
```

#### 冲突处理策略（v0.7新增）

| 场景 | 策略 |
|------|------|
| 3:0 fail | 进入修复层 |
| 2:1 fail | 进入修复层，记录少数派证据 |
| 2:1 pass | 不直接通过，检查少数派是否提出P0/P1风险 |
| 1:1:1 | 触发仲裁器 |
| 异构孤判 fail | 强制证据复核 |
| 同模型孤判 fail | 抽样复核（比例动态提升） |
| 所有法官 uncertain | 不交付，回到蛇头重新分析 |

#### 仲裁器设计（程序化+LLM混合）

仲裁器不是第四个普通法官，而是按以下顺序处理：
1. 检查证据是否完整（所有evidence_refs可追溯）
2. 检查是否有可执行测试
3. 检查是否命中确定性规则
4. 检查是否涉及高风险模式
5. 若仍无法判断 → 调用高能力模型做有限上下文仲裁

#### 投票机制（保留并增强）

- 3:0 → 直接通过/拒绝
- 2:1 角色孤判（不同角色法官独判）→ **100%强制深挖**
- 2:1 同角色不同模型孤判 → 20%抽样（v0.6为5%，角色化后同角色异模型风险降低故提高抽样率）
- 1:2 → 强制深挖
- 1:1:1 → 触发仲裁器 → 仍无法判断 → 人工接管

**反轻信指令（P2验证）：** 所有法官强制4步：列出偏离→比对详细日志→指出不一致→声明无法判断。响应率0/4→4/4(100%)。

**批量审查（P10验证）：** N个模块/修复打包一次调用。-69%法官token，判决一致性80%，零漏检。

**批量审查高风险禁用条件**（以下场景禁止批量，必须逐案裁决）：
- P0/P1级别缺陷
- 跨模块依赖复杂（3+文件交互）
- 修复失败重试产物
- 黑箱重写产物
- 框架约定类问题（如validators的@validator装饰器）
- 安全漏洞
- 公共接口变更
- 数据库迁移
- 批量时要求逐模块独立输出结构化判决（module_id/verdict/confidence/risks/evidence），禁止笼统结论"所有模块均通过"。

**批量审查质量控制：** 每次批量审查记录批量大小、单模块平均token、漏检率、误判率、复核率。成本下降不能以漏检率上升为代价。

### 3.3 修复层

```
A阶段: 修复规划器(Claude)≠蛇身(DeepSeek)
         → 修复蛇(DeepSeek)按指令修改
         → 确定性审计(零token)
              ↓ 发现新bug?
B阶段: 重写蛇(Gemini)≠修复蛇≠蛇身
         → 信息完全隔离（不看原代码实现）
         → 但必须遵守契约约束（看10项输入+边界控制表）
         → 不看原实现，但必须看契约
```

**黑箱重写边界控制**：

| 操作 | 允许 | 说明 |
|------|:----:|------|
| 保持函数签名不变 | ✅ | 默认必须 |
| 修改内部实现 | ✅ | 核心目的 |
| 新增私有辅助函数 | ✅ | 允许 |
| 修改公共API | ❌ | 除非蛇头批准 |
| 新增第三方依赖 | ❌ | 默认禁止 |
| 删除/跳过测试 | ❌ | 禁止 |
| 修改配置文件 | ❌ | 需单独授权 |

**重写产物必须**：通过原测试集。测试不足时审计层要求补充测试，不直接接受重写。

**最小diff原则（v0.7新增）：** 所有修复（包括A阶段和B阶段）遵循最小修改约束：

| 约束 | 说明 |
|------|------|
| 只修改与缺陷直接相关的代码 | 不顺手重构 |
| 不修改无关格式 | 不改变代码风格 |
| 不重命名公共符号 | 保持API稳定 |
| 不引入新依赖 | 保持依赖树不变 |
| 不删除注释 | 除非注释本身错误 |
| 不扩大diff面积 | 非必要修改拆分为后续任务 |

审计层检查diff范围：若超过阈值（50行或3+文件），要求修复层说明"为什么需要这些额外修改？是否与缺陷直接相关？可否拆分为后续任务？"每个patch输出核心修复diff、非必要diff和风险diff三类标注。

**已验证：** P7黑箱重写14/14回归测试通过，防御层从1层→4层。

| 层级 | 检查项 | 技术 | Token | 阻断? |

| L1 | 8种AST危险模式 | 规则引擎 | 0 | ✅ |

| diff超过50行 | 必须L3 |

| 涉及安全敏感函数 | 必须L1强阻断+L3 |

#### 测试生成与可信度审计（v0.7新增）

**修复流程中的测试要求：**

```
Bug Fix 模式：
1. 复现 bug（确认缺陷可触发）
2. 生成失败测试（复现bug的测试用例）
3. 修复代码
4. 测试通过（原失败测试 + 已有测试集）
5. 检查是否引入新失败
```

P0/P1缺陷修复必须附带复现测试。没有复现测试的修复不能标记为高置信度完成。若无法生成失败测试，系统应标记"该修复缺乏回归测试保护"。

**测试可信度检查项：**
- 是否覆盖正常路径/边界路径/异常路径
- 是否覆盖原bug复现路径
- 是否存在空断言（assert True）
- 是否过度mock导致虚假通过
- 是否依赖执行顺序（flaky风险）
- 是否只测试实现细节而非行为
- 是否能捕获回归

#### 人工接管接口（v0.7新增）

系统不可能完全无人参与。以下场景触发人工接管：

| 触发条件 | 动作 |
|---------|------|
| 连续2次修复失败 | 人工接管 |
| 法官 1:1:1 + 仲裁失败 | 人工仲裁 |
| 涉及安全漏洞 | 人工审查 |
| 修改公共API | 人工审查 |
| 测试覆盖率不足且风险高 | 人工审查 |
| 学习层经验冲突（pattern A vs pattern B） | 人工审核 |
| 项目构建架构变更 | 人工确认 |
| 成本超过预算阈值 | 暂停并报告 |

人工接管时系统生成摘要（任务目标/当前diff/失败历史/法官分歧/证据列表/不确定项/推荐方案），而非让人从头阅读所有日志。

### 3.5 学习层

从成功修复/构建中提取模式（4要素）：
```
触发条件 → "if not param:" 用于数值参数
修复模板 → "if param <= 0:"
置信度   → 0.7 → ±0.1(成功) / -0.2(失败)
来源     → bug-185, bug-X, ...
```

**注入策略**：不全局注入。根据当前任务语言/框架/错误类型检索，仅注入Top-3条高置信度模式。每次标注"历史经验，仅供怀疑，不作为结论"。当前证据与历史经验冲突时以当前证据优先。

**模式生命周期**：
```
candidate → 新提取，未充分验证
active    → 连续3次有效
deprecated → 连续2次导致误判
archived  → 长期未命中
```

**失败反模式**：不仅记录"怎么做对"，也记录"哪里容易错"——例如"此类问题曾因过度修改公共函数导致回归""某类法官曾被devlog误导"。失败反模式反向注入蛇头prompt作为警示。

**已验证：** P9从5个bug提取3个模式。预计50+budgets命中率50-70%。

## 四、四维任务空间建模

**状态：✅ v2.0 完整实现**

### 4.1 坐标系

```
       Z (难度) [0, 9]  ×  R (领域风险系数)  =  Z_eff (有效难度)
       ↑
       │  Z_eff < 2 → 快速通道(1蛇头1法官)
       │  Z_eff 2-4 → 标准双审(1蛇头2法官)
       │  Z_eff 4-6 → 交叉验证(2蛇头2法官)
       │  Z_eff 6-8 → 回溯+回归审计(2蛇头3法官)
       │  Z_eff ≥ 8 → 全量审查+人工抽检(3蛇头3法官)
       │
       └──────────────→ Y (领域类型)  ×  R (风险系数)
              ／           code-repair=1.5  formatting=0.7
            ／
          X (时序/优先级)
          │  依赖链自动推导
          │
          V (价值) {普通, 高价值}
            普通 → 标准审查
            高价值 → 三法官+回归审计（3条规则触发）
```

### 4.2 领域风险系数 R

不同领域的基础风险不同。R 值使高风险领域自动获得增强审查，低风险领域走快速通道。

| 领域 | R | 默认蛇头 | 默认法官 | 特殊机制 |
|------|---|---------|---------|---------|
| code-repair | 1.5 | Claude | 3(C1) | 异构裁决+黑箱重写+反轻信+批量 |
| research | 1.5 | Claude | 3(C1) | 人工审查 |
| web-api | 1.4 | Claude | 3(C1) | L3语义审计 |
| code-review | 1.3 | DeepSeek | 3(C1) | 异构裁决 |
| static-analysis | 1.2 | DeepSeek | 2 | — |
| data-io/validation/statistics/persistence/cli | 1.0 | DeepSeek | 2 | — |
| data-modeling | 0.9 | DeepSeek | 2 | — |
| formatting | 0.7 | DeepSeek | 2 | — |

**维度合并规则**：Y域配置与Z_eff配置冲突时，取 max(Y.judges, Z.judges) 和 max(Y.heads, Z.heads)。Y域提供底线，Z_eff提供增强。领域特殊机制与Z_eff额外机制取并集。

### 4.3 任务剖面体系（快递站模型）

**核心思路**：固化经验为矩阵，LLM只做映射，不重新计算。

每个剖面包含：Z值、领域、上下文约束(scale_range/input_signature)、校准历史、来源实验。匹配时 LLM 拆解用户任务 → 匹配剖面名 → 自动获取 Z/R/蛇配置。

**当前已验证的9个剖面：**

| 剖面 | Z | R | Z_eff | 蛇配置 |
|------|---|---|-------|--------|
| code-bug-fix | 4 | 1.5 | 6.0 | 2蛇头3法官+回溯 |
| code-bug-detect | 3 | 1.3 | 3.9 | 1蛇头2法官 |
| data-loader | 3 | 1.0 | 3.0 | 1蛇头2法官 |
| data-cleaner | 4 | 1.0 | 4.0 | 2蛇头2法官 |
| stats-computer | 4 | 1.0 | 4.0 | 2蛇头2法官 |
| report-generator | 3 | 0.7 | **2.1** | 1蛇头2法官 |
| crud-model | 3 | 0.9 | 2.7 | 1蛇头2法官 |
| crud-store | 4 | 1.0 | 4.0 | 2蛇头2法官 |
| cli-entry | 3 | 1.0 | 3.0 | 1蛇头2法官 |

report-generator 的 Z_eff=2.1 展示了领域风险系数的价值：旧预评分蛇误判为 Z=9(重型蛇)，现在 R=0.7 将有效难度拉低到标准双审区间。

### 4.4 V轴触发规则

| 条件 | 触发 | 动作 |
|------|------|------|
| 安全关键词(密码/密钥/token/支付/隐私/权限...) | 任一命中 | 升为高价值 |
| 上游模块法官标记"存疑"≥2次 | 自动触发 | 下游模块升为高价值 |
| 任务在依赖链关键路径且无可替代 | 人工标记 | 升为高价值+抽检 |
| 高价值任务连续5次无异常 | 自动衰减 | 降回普通 |

### 4.5 人类校准回路

```
新任务类型 → 无匹配剖面 → 预评分蛇(Z_raw)
    → ×0.8保守系数 → Z_safe → 执行
    → 收集反馈(蛇头轮次/法官驳回/修复触发)
    → 蛇头1轮+0驳回 → Z可能过高 → 下调Z → 重新验证
    → 法官驳回≥1 → Z可能过低 → 上调Z → 重新验证
    → 验证通过 → 人工审核 → 固化到剖面表(含上下文+校准历史)
    → 固化后终身使用，不再重新评估
```

M4 Reporter 走完了完整链路：预评分Z=9 → 执行发现标准蛇足够 → 人工审核 → 校准Z=3 → 写入剖面表。

## 十二、核心指标体系

### 质量指标
```
缺陷召回率   — 已发现缺陷/总缺陷
缺陷精确率   — 正确发现/总发现
修复一次通过率 — 首次修复即通过审计的比例
回归引入率   — 修复后引入新缺陷的比例
误报率       — 无缺陷代码被标记的比例
人工干预率   — 需要人工介入的任务比例
```

### 成本指标
```
平均token/bug     — 当前~5,000t (E2)
P50/P90 token     — 待收集（当前仅均值）
平均耗时/bug      — 待端到端测量
平均重试次数      — 当前~1.2次/bug
每成功修复总成本  — 含token+工具执行+人工
```

### 裁决指标
```
法官一致率       — 三法官全部一致的比例
异构孤判命中率   — 异构法官独判正确的比例
仲裁触发率       — 需深挖/仲裁的任务比例
批量审查漏检率   — 批量模式下遗漏的缺陷
```

### 模式B指标
```
模块首次集成通过率  — 当前100% (12/12, E4)
接口契约违反次数    — 当前0
集成失败平均修复轮数 — 当前0（首次全部通过）
项目可运行率        — 当前100% (3/3)
```
